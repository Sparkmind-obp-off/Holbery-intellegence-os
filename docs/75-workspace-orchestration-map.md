# 75 — HIO Workspace Orchestration Map (Current → Target)

**Date:** 2026-10-17  
**Purpose:** A concrete implementation map for turning the current chat/planner/proposal features into one coherent agent workspace.  
**Scope:** HIO repository only. This is not proof of runtime readiness.

## 1. Current route inventory from source

### Chat and planning
- `POST /api/v1/agent/chat`: persists chat conversation/messages and calls the existing Groq chat endpoint.
- `GET /api/v1/agent/conversations`
- `GET /api/v1/agent/conversations/:id/messages`
- `POST /api/v1/agent/runs`: generates and persists a structured 3–6 step plan.
- `GET /api/v1/agent/runs`
- `GET /api/v1/agent/runs/:id`
- `POST /api/v1/agent/runs/:id/steps/:sequence/execute`: only the `research.search` tool is executable today, with explicit approval and provider preflight.

### Coding proposal
- `POST /api/v1/agent/code-tasks`: currently requires 1–3 explicit target file paths; calls Groq to propose full-file replacements.
- `GET /api/v1/agent/code-tasks`
- `GET /api/v1/agent/code-tasks/:id`
- `POST /api/v1/agent/code-tasks/:id/submit`: explicit approval may create a Git branch and draft PR if `GITHUB_TOKEN` is configured.

### Explicitly not present in v1
- automatic repository/file discovery for coding tasks;
- disposable sandbox creation and lifecycle;
- server-side execution of allowlisted commands;
- actual command/test result persistence;
- bounded automatic repair loop;
- cancellation, timeout recovery, orphan cleanup and resumable orchestration;
- unified artifact manifest/private download;
- an end-to-end task view that unifies plan, research, coding, tests, repairs and delivery;
- verified live provider account access and verified production parity.

## 2. Target task model

Create one canonical task/run envelope and link specialized records rather than maintaining unrelated chat, agent-run and coding-task flows.

Minimum fields:
- stable task ID and authenticated owner ID;
- objective, task type, approved scope, risk class and requested deliverables;
- immutable repository base SHA when code is involved;
- current state, attempt number, cancellation request, created/updated/start/end timestamps;
- budget reservation (model calls, sandbox time, command count, repair count; monetary cost only if provider returns reliable usage);
- provider/sandbox execution status and external operation IDs;
- links to plan, steps, tool receipts, diffs, test report, artifacts and audit events.

Do not blindly rename or replace current tables. Inspect all existing migrations, constraints and consumers; use additive migration(s) and an explicit mapping from legacy `agent_runs` / `agent_code_tasks` to the canonical task envelope. Keep the first implementation narrow if a full unification would introduce migration risk.

## 3. Canonical finite state machine

Recommended high-level state:
`queued → planning → awaiting_task_approval → running → validating → repairing → review_ready`

Allowed terminal outcomes:
`completed`, `failed`, `blocked`, `cancelled`.

Use explicit step-level states:
`pending`, `running`, `awaiting_approval`, `passed`, `failed`, `skipped`, `blocked`, `cancelled`.

Rules:
- A validated plan can be shown immediately, but is not “running” until dispatch is persisted.
- A single task-level approval may authorize a declared budget and a set of low-risk read/build/test tools for that task. Do not prompt before every harmless step if the task-level grant covers it.
- Publishing a PR, posting externally, sending messages, paying, changing secrets, running production migrations or deploying always requires a separate explicit approval at the point of action.
- A missing provider, unavailable real sandbox, skipped test or fake adapter is BLOCKED, not completed.
- Persist each state transition and external side-effect receipt before reporting it to the client.
- Cancellation must stop new work, signal any active sandbox command and reconcile cleanup.
- On Worker restart, reconcile tasks in running/preparing/testing states against stored external IDs; never blindly dispatch a duplicate.

## 4. Tool registry contract

Every tool must be a server-owned registry entry, never an arbitrary name generated by the model:
- stable tool ID and version;
- input/output Zod schema;
- risk/side-effect class;
- required task-level grant;
- provider prerequisites;
- timeout/output cap/cost or usage ceiling;
- idempotency behavior;
- executor adapter and typed error mapping;
- audit/event schema.

Suggested capability progression:
1. `research.search`: existing pipeline; provenance-bearing results; task-level grant and daily/provider limits.
2. `workspace.analyze`: inspect bounded repository files or task artifacts; read-only.
3. `coding.plan`: create structured file/patch plan; no writes.
4. `coding.edit`: apply validated patch inside a disposable sandbox only.
5. `quality.check`: run a server-approved command set in the sandbox; capture actual results.
6. `coding.repair`: bounded patch attempt based on actual failure output; cannot expand task scope or permissions.
7. `artifact.package`: generate manifest and bounded private artifacts.
8. `github.draft_pr`: separate approval-gated publish action in control plane.
9. `validation.record`: record evidence, experiment, decision and next step.

Do not register tools whose executor is missing. Do not mark `workspace.analyze`, `artifact.draft` or `quality.check` executable until a real implementation and tests exist.

## 5. Orchestrator responsibilities

Implement a deterministic server-side orchestrator:
1. validate/authenticate request and task owner;
2. reserve budget atomically before provider calls;
3. generate a structured plan and validate it;
4. persist plan/steps/events;
5. evaluate policy and task-level grant;
6. dispatch the next allowed step;
7. persist tool input digest, result receipt and transition;
8. on failure, classify retryable vs terminal;
9. for coding failures, permit at most two repair attempts by default and rerun only the approved command set;
10. stop on cancellation, timeout, budget cap, provider auth/quota error, repeated failure, policy violation or sandbox health failure;
11. produce review-ready summary and require explicit approval for external side effects.

No open-ended while-loop. Every execution has hard caps for elapsed time, step count, model calls, sandbox minutes, command count, output bytes and repair attempts. Enforce these on the server, not only in prompts/UI.

## 6. Coding adapter boundary

Use a provider-neutral interface in HIO and a Daytona implementation only after verifying current API, account access and permitted spend. Do not invent SDK methods from memory.

The adapter must support, or clearly mark unsupported:
- create disposable workspace pinned to repository and base SHA;
- bounded file listing/read/write and patch application;
- execute one server-allowlisted command with timeout;
- read exit code and bounded output;
- cancellation and termination;
- diff generation and artifact export;
- cleanup and cleanup verification.

If Daytona cannot provide a required security boundary, document the gap and do not claim safe execution. Fake adapters are for unit tests only. Never pass Cloudflare/GitHub credentials or host environment into the sandbox.

## 7. UI acceptance contract

The workspace must display one task timeline with:
- objective and declared deliverables;
- plan and currently executing step;
- permission/budget grant and consumed budget;
- step status and truthful execution provider (real or mocked);
- research sources with URLs/timestamps;
- code diff and changed file list;
- actual commands with exit codes and PASS/FAIL/SKIPPED/BLOCKED;
- bounded repair attempts and final failure reason;
- artifacts and expiry/access information;
- final decision and explicit next action.

The UI must distinguish:
- **Planned:** model generated a plan only.
- **Running:** a real executor was dispatched and the task state persisted.
- **Review ready:** checks actually ran and a diff is available for review.
- **Completed:** only for a task whose defined acceptance criteria actually passed.
- **Blocked:** provider/configuration/sandbox unavailable or required checks could not run.
- **Failed:** execution happened and failed its defined criteria.

No green status based solely on model text.

## 8. Manual test scenarios

No GitHub Actions/workflows. Execute these in a verified local checkout or isolated sandbox and retain output:
- chat conversation ownership and malformed IDs;
- plan schema rejection and provider timeout/quota;
- task-level grant accepted once, rejected for another owner or changed scope;
- two concurrent submissions cannot overspend quota;
- duplicate step dispatch produces one side effect;
- provider outage produces BLOCKED with no pretend result;
- repository prompt injection cannot add a tool or command;
- path traversal, absolute path, symlink escape and sensitive-file near misses are rejected;
- approved command passes; unapproved/deploy/destructive command is denied;
- test failure triggers bounded repair; successful repair reruns tests;
- repeated failure stops at the cap;
- cancellation and timeout terminate work and clean sandbox;
- task resumes after simulated Worker interruption without duplicate work;
- artifact access by another owner is denied;
- publishing without exact diff/base approval is denied;
- GitHub API failure mid-publish is reconciled safely;
- all existing founder, research, chat, agent and coding routes regress cleanly.

## 9. Do not merge these conflicting paths

- PR #10 currently describes validation via GitHub Actions check runs and changes the Actions workflow. Do not merge/use it as-is under the no-workflows policy. Port only the useful concepts into the HIO sandbox runner with stored real command receipts.
- PR #11 is the draft change removing the known workflow and updating the manual-verification/engine specs. It is not merged; therefore main still contains `.github/workflows/agent-runtime-check.yml` at the time of this audit.
- Keep manual verification independent of GitHub Actions, GitHub Checks, and workflow artifacts.

## 10. Definition of “real AI agent workspace”

Do not call the product complete until a user can submit one objective and the system can, without manual path selection or repeated per-step babysitting for pre-approved low-risk tools:
- understand and persist a plan;
- execute the tools it actually has permission and adapters for;
- research and preserve evidence;
- inspect and change code in a disposable sandbox;
- run real tests and repair failures within budget;
- resume or cancel safely;
- deliver a diff, logs, test report and artifacts;
- ask only at genuine approval boundaries;
- report truthful cost/usage and explicit limitations;
- pass manual regression and security tests with recorded output.

A final human review before publishing/merging/deploying remains a deliberate safety boundary, not a defect.
